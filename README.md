# Ordo — дела в порядке

ИИ-секретарь руководителя: приложение и веб-версия. Загружайте файлы,
подключайте почту и календари — Ordo ищет по всему с первых букв,
извлекает задачи из материалов и ведёт их на канбан-доске со статусами,
как в CRM. ИИ — модели Kimi (Moonshot AI) и Qwen (Alibaba) через единый шлюз.

См. [`PLAN.md`](./PLAN.md) — архитектура, модели данных, порядок реализации
и явные решения по спорным местам задания.

## Стек

- `apps/api` — FastAPI (Python 3.12), SQLAlchemy 2, Alembic, Pydantic v2.
- `apps/worker` — фоновые задачи на arq + Redis: извлечение текста и задач
  из файлов, синхронизация календарей.
- `apps/web` — Next.js (App Router), TypeScript, Tailwind, dnd-kit.
- PostgreSQL 16 (`pgvector`, `pg_trgm`), Redis, MinIO (S3-совместимое
  хранилище; в проде — российский провайдер).

## Быстрый старт

```bash
cp .env.example .env
# при необходимости отредактируйте .env (ключи ИИ, DATA_RESIDENCY и т.д.)
docker compose up --build
```

После старта:

- API: http://localhost:8000 (`/healthz`, `/docs`)
- Веб: http://localhost:3000
- MinIO консоль: http://localhost:9001

Миграции применяются автоматически сервисом `migrate` перед стартом `api`.

Путь по умолчанию: открыть http://localhost:3000 → зарегистрироваться →
попасть на экран «Сегодня» с пятью статусами доски («Входящие», «В
работе», «Ждёт ответа», «На согласовании», «Готово»), поиском, разделами
«Задачи», «Файлы» и «Календари».

## Возможности по этапам

1. **Основа** — регистрация/вход (argon2 + JWT в httpOnly cookie), полная
   изоляция данных по `user_id`, healthcheck, структурированные логи без
   содержимого пользовательских данных.
2. **Канбан** — CRUD задач и статусов, перетаскивание карточек (dnd-kit)
   с транзакционным пересчётом `position`, фильтры, экран «Сегодня» с
   объяснением приоритета.
3. **ИИ-шлюз** — единый интерфейс `LLMProvider` над Kimi/Qwen/Qwen-VL/
   собственным vLLM и mock-провайдером для тестов; маршрутизация по типу
   задачи, ретраи, структурированный вывод, `AiCallLog`, правило
   резидентности (см. ниже).
4. **Файлы → задачи** — приём PDF/DOCX/XLSX/CSV/PPTX/EML/MSG/ICS/изображений
   (включая HEIC и сканы через Qwen-VL OCR), извлечение задач с защитой от
   выдумок (цитата обязана быть в исходном тексте), дедупликация,
   предложения с подтверждением на экране «Файлы».
5. **Календари** — импорт `.ics`, синхронизация CalDAV (Яндекс, iCloud) раз
   в 15 минут без дублей по UID, «В задачи» / «Добавить все». Google
   Calendar и обратная синхронизация — за фиче-флагом / TODO.
6. **Поиск** — `GET /search?q=` по задачам, файлам, событиям и людям с
   первых двух букв; смысловой поиск по эмбеддингам для длинных запросов;
   ранжирование по совпадению, кликам, давности и времени суток.

## Переменные окружения

Все переменные описаны в [`.env.example`](./.env.example). Ключевые:

- `DATA_RESIDENCY=ru` — запросы с пользовательскими данными идут только на
  `selfhost` (собственный vLLM-сервер); `DATA_RESIDENCY=dev` разрешает
  облачные `kimi`/`qwen`. Действует и для чата, и для эмбеддингов.
- `MOONSHOT_*`, `DASHSCOPE_*`, `SELFHOST_*` — ключи и модели провайдеров ИИ.
- `AI_ROUTING` — путь к `config/ai_routing.yaml`, где задан выбор провайдера
  по типу задачи (`extract_tasks_short/long`, `vision_ocr`, `draft_reply`,
  `summary`) и `fallback` для каждой.
- `GOOGLE_CALENDAR_ENABLED` — фиче-флаг для Google Calendar (по умолчанию
  выключен; сам OAuth не реализован, это следующий этап).
- `MAX_UPLOAD_MB`, `RATE_LIMIT_UPLOAD`, `RATE_LIMIT_AI` — лимиты загрузки и
  ИИ-запросов на пользователя.

## Смена модели / провайдера ИИ

1. Отредактируйте `KIMI_MODEL`, `QWEN_MODEL`, `QWEN_VL_MODEL` или
   `SELFHOST_MODEL` в `.env`.
2. Проверьте, что модель ещё существует у провайдера (идентификаторы
   меняются часто):
   ```bash
   make check-models
   # или: cd apps/api && python -m ordo_api.ai.check_models
   ```
3. При необходимости измените маршрутизацию по типам задач в
   `config/ai_routing.yaml` — код менять не нужно.

## Подключение собственного vLLM-сервера

`SELFHOST_BASE_URL` и `SELFHOST_MODEL` указывают на любой OpenAI-совместимый
эндпоинт (например, vLLM с `--served-model-name`). При `DATA_RESIDENCY=ru`
это единственный провайдер, к которому уходят запросы с содержимым
пользовательских данных (извлечение задач, эмбеддинги, OCR).

## Разработка

```bash
# API
cd apps/api
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest

# Worker (использует модели и ИИ-шлюз из apps/api как редактируемую зависимость)
cd apps/worker
python3 -m venv .venv && source .venv/bin/activate
pip install -e ../api
pip install -e ".[dev]"
pytest

# Веб
cd apps/web
npm install
npm run dev        # http://localhost:3000
npm run typecheck
npm run build
```

Быстрые команды через `Makefile`: `make up`, `make down`, `make test-api`,
`make test-worker`, `make test-web`, `make check-models`, `make eval`, `make lint`.

## Тесты и качество

- **pytest** — 50 тестов API + 21 тест воркера, все на провайдере `mock`
  (никакой реальный ИИ/сеть не нужны). Покрыты: аутентификация, канбан
  и транзакционное перемещение карточек, экран «Сегодня», ИИ-шлюз
  (маршрутизация, фолбэк, повтор при невалидной схеме, правило
  резидентности с тестами на `ru`/`dev`), приём и разбор файлов всех
  форматов, дедупликация и защита от выдуманных цитат, календари и
  идемпотентный CalDAV-sync, поиск и ранжирование, удаление аккаунта.
- **`tests/fixtures/`** — реальные документы для тестов и `make eval`:
  письмо (`pismo.eml`), договор с текстовым слоем (`dogovor.pdf`), скан
  без текстового слоя (`schet-scan.pdf` + `skan.png`), таблица
  (`plan.xlsx`), календарь (`vstrechi.ics`).
- **`make eval`** — прогоняет часть фикстур через реальную модель, если в
  `.env` заданы ключи ИИ и `DATA_RESIDENCY=dev` (либо настроен
  `SELFHOST_BASE_URL`), и печатает точность извлечения задач. Без ключей
  или при `DATA_RESIDENCY=ru` без `SELFHOST_BASE_URL` — команда объясняет
  почему пропущена и завершается успешно (это ожидаемое поведение, а не
  ошибка).
- **Playwright** (`apps/web/e2e/`) — сценарий «зарегистрировался → создал
  задачу на доске → перетащил карточку в «Готово»» и связанный сценарий
  для файлов/предложений. Запуск: `cd apps/web && npx playwright test`
  (нужен запущенный `docker compose up`, так как тест ходит в реальный API).
- **CI** (`.github/workflows/ci.yml`) — на каждый push/PR: lint и тесты
  API, тесты воркера, typecheck и сборка веба.

## Безопасность

- Пароли — argon2, сессии — JWT в httpOnly cookie (`SameSite=Lax`).
- Все данные строго изолированы по `user_id` на уровне каждого запроса.
- Ключи ИИ никогда не попадают на фронтенд; веб обращается только к
  собственному API.
- Загрузка проверяет реальный тип файла по содержимому (`python-magic` +
  сниффинг OOXML/ICS/EML), а не только по расширению.
- Логи структурированные (`structlog`), без содержимого пользовательских
  данных и без текста запросов/ответов ИИ — только метаданные вызова.
- Шифрование файлов — на уровне бакета (SSE в MinIO/S3-провайдере);
  прикладной код не хранит и не логирует содержимое файлов.
- `DELETE /auth/me` необратимо удаляет аккаунт: файлы из хранилища,
  фрагменты и эмбеддинги, задачи и предложения, календари и события,
  логи ИИ-вызовов, историю поисковых кликов.
- Rate limit (`slowapi`) на загрузку файлов на пользователя; путь к ИИ
  идёт только через загрузку файлов и подчиняется тому же лимиту.
- `npm audit` в `apps/web` показывает известные advisories для Next.js 14.2.x
  (актуальная патч-версия линии 14) и для dev-зависимости `eslint-config-next`;
  оба фикса требуют мажорного перехода на Next 16 (ломающие изменения).
  Приложение не использует `next/image`, i18n-мидлвары и открытые
  `remotePatterns` — основные векторы этих advisories, поэтому переход
  отложен как решение вне рамок MVP; при обновлении до Next 16 стоит
  перепроверить этот раздел.
